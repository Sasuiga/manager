## 1. 背景与目标

### 1.1 项目背景

本项目是一款以 12 个月为周期的单机生产经营刷分游戏。现有系统包含采购、生产、销售、员工、设备、卡牌、事件、研发、知识产权、融资、董事会目标及财务报表等机制。

本轮讨论形成的核心设计判断是：

> 玩家真正的核心活动只有采购、生产与销售。其他系统都应为这三个核心活动提供能力、改变约束或制造环境变化，而不应与三环争夺主游戏的位置。

三环分别承担以下设计职责：

- 采购：决定玩家提前承担什么价格、库存和现金占用风险；
- 生产：决定如何把有限原料和产能转换为产品组合；
- 销售：决定以何种价格、确定性和市场投入兑现收益。

当前项目已有约 9600 行代码，并已经具备完整的库存计价、复式记账、结算报告和 UI 基础。完全重写纯三环版本会重复实现大量成熟底层能力，也会产生两套状态、结算和测试。因此未选择另起炉灶。

### 1.2 本轮目标

采用“同代码库核心实验分支”的方式：

1. 保留当前完整模式；
2. 增加可切换的核心循环实验模式；
3. 在核心模式中暂时关闭员工、卡牌、研发、董事会等增量系统；
4. 复用现有库存、现金、财务和结算引擎；
5. 优先验证采购—生产—销售本身是否形成足够深度；
6. 核心结构验证后合回主干，再逐层恢复增量系统。

核心实验分支不应长期发展成第二套产品。理想流程是：

```text
实验分支验证核心
        ↓
确认三环结构与数值
        ↓
合并回主干
        ↓
逐层恢复设备、员工、融资、事件、研发、卡牌和董事会
```

### 2.4 生产计划已由单产品改为多产品矩阵

原状态：

```ts
plan: {
  tier: Tier | null
  qty: number
  overtime: boolean
}
```

现状态：

```ts
plan: {
  quantities: Record<Tier, number>
  overtime: boolean
}
```

新增或调整：

- `setPlan(state, tier, qty)`：设置单条产品线排产；
- `plannedTotal(state)`：计算全月总排产；
- 所有产品线共享同一个产能池；
- `maxProducible` 会扣除其他产品线已经预留的产能；
- 对共享原料进行计划预留，避免同一批原料被多条线重复分配；
- `confirmProduction` 一次确认并生产多条产品线；
- 确认后各线计划清零，不跨月保留；
- 月末自动生产路径同样支持多条产品线；
- 结算报告新增 `production.lines`，同时保留聚合字段以减少 UI 破坏。

原因：单产品计划会把生产阶段退化为“选择当前最赚钱产品并拉满”，无法形成产品组合、稀缺原料分配和订单/现货竞争。多产品排产是三环玩法成立的必要前提。

关键文件：

- `src/core/actions.ts`
- `src/core/settle.ts`
- `src/ui/screens/Turn.tsx`
- `src/ui/App.tsx`

### 2.9 已修复订单与排产联动

核心模式不再用“当前已入库成品”作为自然订单接取条件，而是使用：

```text
可承诺量 = 现有成品库存 + 本月已安排排产
          − 强制订单占用
          − 其他已接自然订单占用
```

当前行为：

- 没有足够可承诺量时，订单按钮不可用；
- 已接订单按接单顺序占用可承诺量；
- 排产减少后，无法足额履约的已接订单自动取消；
- 自动取消的订单不会进入“已放弃”列表，增加排产后可以重新接取；
- 增加排产不会自动替玩家重新接单；
- 完整模式仍沿用“现有库存”校验，不改变原有即时生产规则。

关键实现：

- `committableProductQty()`
- `availableForOrder()`
- `canAcceptOrder()`
- `reconcileAcceptedOrders()`
- `setPlan()` 中的订单重整合

相关测试位于 `src/core/core-loop.test.ts` 的“订单与排产联动”部分。

### 2.10 核心模式采购已计划化

普通月度采购不再在点击时立即扣款入库。核心模式当前流程为：

```text
制定采购计划
→ 制定生产计划
→ 制定销售计划
→ 查看经营预演
→ 正式结算时采购入库、生产、销售
```

具体规则：

- 同一原料可在结算前切换小批、中批、大批或取消采购；
- 采购计划按当前价格、供给和仓容计算实际计划到货量；
- 采购计划不立即减少账面现金，但会形成“计划支出”和“计划后可用现金”；
- 多项采购计划不能重复使用同一笔现金；
- 生产可用原料为现有库存加计划到货；
- 如果采购计划已经被排产占用，不能直接减少或取消，必须先调整生产；
- 正式结算先执行采购入库和付款，再执行生产与销售；
- 完整模式仍使用原有即时采购，不受影响。

采购页会显示当前库存、计划到货、计划支出、计划后可用现金和已选采购档数。预演页的采购支出和期末现金区间已接入采购计划。

相关测试位于 `src/core/core-loop.test.ts` 的“核心模式采购计划”部分。

### 2.11 采购与生产计划双向联动

核心模式修改采购计划时不再要求玩家先手动调整生产安排，而是按以下规则自动联动（`setPurchasePlan`）：

| 操作 | 行为 |
|---|---|
| 增加/更换采购档，新采购量 ≥ 生产 BOM 需求 | 直接允许 |
| 减少采购档，新采购量 < 生产需求 | 允许，原生产计划（含加班标志）整体清空并同步已接订单，日志提示重排产 |
| 取消采购 | 生产计划仍非空时同样允许，一并清空（避免原料悬空）；生产计划为空时直接放行 |
| 现金不足、档数用满 | 照旧拒绝 |

关键实现：

- `purchasePlanClearsProduction()` / `clearProductionPlan()`（`src/core/actions.ts`）
- 采购确认弹窗会提示“确认后生产计划将清空”

原因：双向锁死（改采购必须先去动生产）使玩家在三环间来回穿梭，摩擦大于收益；清空后重排产一次完成，且订单由 `reconcileAcceptedOrders` 保持一致。

### 2.12 采购计划执行后清空档位

`executePlannedPurchases()` 入库后清空所有原料 `chosenLot` 并重置 `lotsUsed`。

原因：生产可用原料口径为“库存 + 计划到货”，若计划已入实体库存但档位保留，后续派生量（排产上限、订单可承诺量、立即确认生产路径）会重叠加计划量，造成预演与结算口径偏差。

### 2.13 核心模式生产在结算时统一执行

核心模式不再支持“确认生产安排”即时扣料入库：

- `confirmProduction()` 对核心模式返回“核心模式生产在结算时统一执行”；
- 生产页隐藏确认按钮与确认弹窗，排产只在结算时一次过账。

完整模式保留原有即时确认路径，不受影响。

### 2.14 采购页库存占用展示

核心模式采购表在价格水平后增加“库存占用”列，显示 `(库存 + 计划到货)/仓库上限`，帮玩家在选档前判断仓容截断风险；“采购计划汇总”卡片继续展示计划支出与计划后可用现金，表格不另加合计行。

### 2.15 研发放置模型与 IP 技能树（restore/rnd，2026-09-25）

背景：核心模式开局全产品解锁，玩家会无脑选高端产品；恢复研发部门后把「解锁产线」变成决策，开局仅低端，中端作为教学解锁。

**开局状态**：

- `newGame` 去掉核心模式全解锁 hack：两种模式均只 built 低端（`game.ts`）；
- 六个固定场景预置 1 名研发人员（`scenarios.ts` 的 `rndStaff ?? 1`），并清空研发项目/放置/知产，开局知产树为空。

**放置模型**（计划层，同采购/排产，结算执行、月初清零）：

| 项 | 规则 |
|---|---|
| 放置 | `ResearchSlot.assigned`；池上限 = 研发人数（每部门上限 5 人）；首次放置自动立项（计入 `rndStartsQ` 董事会指标） |
| 进度 | 每项目 = 放置人数 × 5/月 + 事件/知产平修正（`rndProjectOutcome`，derive 层） |
| 成功率 | 基础 + 放置人数 × 5%，封顶 90%（`RND_RATE_CAP`）；中端教学项 `rateCap: 100`（1 人即 100%） |
| 在研判定 | 已立项且本月放置 ≥ 1；费用 = 3w × 在研项目数（并行研发有成本） |
| 失败 | 进度保留（不重置），下月可重投 |
| 结算顺序 | 研发段从原 §3 提前到生产之前（0 协议 → 1 研发 → 2 生产 → 3 销售 → 4 过账）：解锁当月排产即可生产 |

**项目数值**（`data/game.ts` RND_PROJECTS）：

| 项目 | 需求 | 基础成功率 |
|---|---|---|
| 中端 BOM | 15 | 95%（封顶 100%，教学） |
| 高端 BOM | 50 | 60% |
| 特殊 BOM | 50 | 45%（揭示新材料） |

**IP 技能树**（替代原「普通/强力池随机抽 1 项」）：三分支 × 三阶段，确定性授予固定知产（`def.ipId`），前置节点完成后方可研究下游：

| 分支 | 阶段 1（15 / 80%） | 阶段 2（30 / 70%） | 阶段 3（50 / 60%） |
|---|---|---|---|
| 供应线 | 采购网络 I3 | 供应链联盟 J2 | 成本转移 J4 |
| 渠道线 | 订单网络 I9 | 渠道垄断 J8 | 品牌壁垒 J3 |
| 装备线 | 设备专利 I2 | 自动化产线 J1 | 研发突破 J6 |

## 4. 已知风险与待确认问题

### 4.1 核心模式参数只是临时值

当前核心模式固定 4 个采购档、2 个订单、全产品解锁。这些设置的目的只是让三环能够立即运行，还没有经过平衡验证。（后续进展：采购档数/订单数已改为 staff 驱动，见「三线人员」节；开局解锁范围已由 §2.15 定案为仅低端。）

待确认：

- 基础采购档数应该是 3、4 还是按月变化；
- 每月订单数量和订单量；
- 哪些产品应在核心模式开局解锁；
- 初始产能、现金和库存；
- 是否保留高级产品所需的新材料开发。

### 4.2 核心模式目前跳过事件，市场月内变化不足

核心模式仍有季度气候变化，但不抽月度事件。因此同一季度内价格与需求可能较稳定。

这有利于先验证确定性核心，但之后需要确认核心市场输入应当如何变化：

- 固定场景；
- 月初公开市场卡；
- 只保留即时市场事件；
- 或保留气候但移除事件选择。

建议坚持“随机性在月初生成问题，玩家作出决策后不再随机否定结果”。

### 4.3 订单规则仍需重新验证

当前订单规则为当月产生、当月接取、当月交付，库存不足则部分交付并失效。该规则可运行，但尚未证明能产生足够的“确定订单 vs 风险现货”张力。

待确认：

- 订单是否应先于采购和生产展示；
- 订单是否需要违约惩罚；
- 订单价格是否一定高于现货；
- 订单是否占用自然需求；
- 是否需要跨月订单。现阶段不建议直接增加跨月复杂度，先验证当月模型。

### 4.4 销售目前仍偏自动结算

玩家能够分配销售资源和选择订单，但现货仍按需求自动成交。销售决策是否足够深尚未验证。

待确认：

- 销售资源用于扩量、提价还是获取订单；
- 同一种资源能否在这些用途间竞争；
- 是否需要玩家主动选择售价档位；
- 现货风险如何体现而不引入结算后随机惩罚。

### 4.5 多产品月末自动生产路径需要更多测试 ✅ 已定案（2026-09-23）

核心模式已取消“确认生产”即时扣料路径，统一在结算执行（§2.13）；完整模式保留显式确认。月末自动处理仍使用独立的内部 `maxProducible`，后续考虑提取统一的生产模拟/执行函数，避免 `actions.ts` 和 `settle.ts` 存在两份近似逻辑。

### 4.6 生产确认后不能撤销 ✅ 已定案（2026-09-23）

采用“先规划、最后统一执行”：核心模式所有三环计划（采购、生产、销售）在结算时一次过账，结算前可反复调整；完整模式保留即时确认路径。

### 4.7 实验分支不能长期与主干分叉

如果该分支持续数月，会导致完整模式和核心模式的状态、UI、结算逻辑发生漂移。完成经营沙盘和第一轮核心验证后，应尽快决定：

- 合并回主干；
- 继续迭代但定期变基；
- 或放弃实验并保留检查点。

当前状态：✅ 已解决（2026-09-24）——`experiment/core-loop` 已 --no-ff 合入 main（`5a27f07`）；增量恢复改在 main 上逐层短期分支进行（restore/staff → restore/equipment → …），每层单独验证、单独可回退。
