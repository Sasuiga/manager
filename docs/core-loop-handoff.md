# 核心三环改造交接文档

> 更新时间：2026-09-23  
> 当前分支：`experiment/core-loop`  
> 当前检查点：`1422068 feat: add core-loop mode and multi-line production`

## 1. 背景与目标

### 1.1 项目背景

本项目是一款以 12 个月为周期的单机生产经营刷分游戏。现有系统包含采购、生产、销售、员工、设备、卡牌、事件、研发、知识产权、融资、董事会目标及财务报表等机制。

本轮讨论形成的核心设计判断是：

> 玩家真正的核心活动只有采购、生产与销售。其他系统都应为这三个核心活动提供能力、改变约束或制造环境变化，而不应与三环争夺主游戏的位置。

三环分别承担以下设计职责：

- 采购：决定玩家提前承担什么价格、库存和现金占用风险；
- 生产：决定如何把有限原料和产能转换为产品组合；
- 销售：决定以何种价格、确定性和市场投入兑现收益。

当前项目已有约 9600 行代码，并已经具备完整的库存计价、复式记账、结算报告和 UI 基础。完全重写纯三环版本会重复实现大量成熟底层能力，也会产生两套状态、结算和测试。因此未选择另起炉灶。

### 1.2 本轮目标

采用“同代码库核心实验分支”的方式：

1. 保留当前完整模式；
2. 增加可切换的核心循环实验模式；
3. 在核心模式中暂时关闭员工、卡牌、研发、董事会等增量系统；
4. 复用现有库存、现金、财务和结算引擎；
5. 优先验证采购—生产—销售本身是否形成足够深度；
6. 核心结构验证后合回主干，再逐层恢复增量系统。

核心实验分支不应长期发展成第二套产品。理想流程是：

```text
实验分支验证核心
        ↓
确认三环结构与数值
        ↓
合并回主干
        ↓
逐层恢复设备、员工、融资、事件、研发、卡牌和董事会
```

## 2. 已完成的工作与关键决策

### 2.1 已建立实验分支

- 分支：`experiment/core-loop`
- 检查点提交：`1422068`
- 提交说明：`feat: add core-loop mode and multi-line production`

原因：避免在主干上直接改造时，由既有卡牌、员工、事件和董事会目标干扰对核心玩法的判断；同时复用现有成熟底层，避免复制项目。

### 2.2 增加运行模式

新增类型：

```ts
type GameMode = 'full' | 'core'
```

`GameState` 新增 `mode`，`newGame(seed, mode)` 默认仍为 `full`，因此原有测试和调用方保持兼容。

标题页现在提供两个入口：

- 核心循环实验：进入 `core` 模式；
- 开始新的一局：进入原有 `full` 模式。

关键文件：

- `src/core/types.ts`
- `src/core/game.ts`
- `src/core/engine.ts`
- `src/ui/useGame.ts`
- `src/ui/App.tsx`
- `src/ui/screens/Title.tsx`

### 2.3 核心模式暂时绕过增量流程

核心模式目前：

- 不进入董事会阶段；
- 不进入事件和抽卡阶段；
- 不显示运营部与研发部入口；
- 不显示招聘区；
- 每月直接进入经营阶段；
- 仍保留季度气候变化、财务结算和 12 个月终局；
- 不会因董事会目标失败出局，因为核心模式不生成目标；
- 仍会因月末现金为负而失败。

为了使没有员工系统的核心模式可以独立运转，暂时给予：

- 每月 4 个采购档位；
- 每月 2 个基础订单；
- 全部产品线视为已解锁；
- 原有基础销售资源；
- 原有初始设备和产能。

这些是实验参数，不应被视为最终正式数值。

### 2.4 生产计划已由单产品改为多产品矩阵

原状态：

```ts
plan: {
  tier: Tier | null
  qty: number
  overtime: boolean
}
```

现状态：

```ts
plan: {
  quantities: Record<Tier, number>
  overtime: boolean
}
```

新增或调整：

- `setPlan(state, tier, qty)`：设置单条产品线排产；
- `plannedTotal(state)`：计算全月总排产；
- 所有产品线共享同一个产能池；
- `maxProducible` 会扣除其他产品线已经预留的产能；
- 对共享原料进行计划预留，避免同一批原料被多条线重复分配；
- `confirmProduction` 一次确认并生产多条产品线；
- 确认后各线计划清零，不跨月保留；
- 月末自动生产路径同样支持多条产品线；
- 结算报告新增 `production.lines`，同时保留聚合字段以减少 UI 破坏。

原因：单产品计划会把生产阶段退化为“选择当前最赚钱产品并拉满”，无法形成产品组合、稀缺原料分配和订单/现货竞争。多产品排产是三环玩法成立的必要前提。

关键文件：

- `src/core/actions.ts`
- `src/core/settle.ts`
- `src/ui/screens/Turn.tsx`
- `src/ui/App.tsx`

### 2.5 保留并复用了现有成熟能力

本轮没有重写以下系统：

- 原料批量采购；
- 五档价格；
- 库存容量；
- 移动加权平均计价；
- BOM 领料；
- 成品库存入账；
- 订单与现货销售；
- 销售收入和销售成本结转；
- 复式记账；
- 资产负债表；
- 月度结算报告；
- 确定性随机数；
- 现有完整模式。

原因：这些部分已经通过多种子会计审计，重写收益低、风险高。

### 2.6 已增加多产品排产测试

新增测试覆盖：

- 核心模式下低端和中端同时排产；
- 两条产品线共享原料；
- 一次确认同时生产两条线；
- 原料正确扣减；
- 产品正确入库；
- 确认后生产计划清零。

当前全部测试通过，会计恒等式最大偏差仍为 0。

## 3. 未完成项与下一步

### 3.1 下一阶段最高优先级：三环统一经营沙盘

当前只是“技术上支持多产品生产”，还没有完成核心玩法验证。采购、生产、销售仍分别位于不同页面，玩家难以看到一项调整对整条经营链的影响。

下一步应建立统一经营预览，使玩家在结算前同时看到：

| 区域 | 至少应显示 |
|---|---|
| 市场 | 各产品自然需求、销售资源带来的额外需求、售价 |
| 订单 | 可接订单、已接数量、交付价格、缺口 |
| 采购 | 当前库存、采购量、采购成本、采购后库存 |
| 生产 | 分产品排产、产能占用、BOM 消耗、原料缺口 |
| 销售 | 预计订单交付、预计现货成交、预计期末成品库存 |
| 财务 | 预计收入、销售成本、毛利、期末现金 |

目标不是立刻合并三个页面，而是先建立一个共享的、实时更新的经营预览模型。

建议先在核心层新增纯只读函数，例如：

```ts
interface OperatingPreview {
  purchases: ...
  production: ...
  sales: ...
  cashEnd: Money
  revenue: Money
  grossProfit: Money
  materialShortages: ...
  productEndingInventory: ...
}

function previewOperations(state: GameState): OperatingPreview
```

预览与实际结算必须尽量复用同一套规则，避免 UI 预测与月底结果不一致。

### 3.2 补足核心模式专属测试

建议新增 `src/core/core-loop.test.ts`，覆盖：

1. 核心模式开局直接进入经营阶段；
2. 核心模式不会生成董事会目标、卡牌和研发活动；
3. 每月生成基础订单；
4. 结算后直接进入下一个经营月；
5. 核心模式能跑满 12 个月；
6. 多产品生产后的订单和现货结算正确；
7. 核心模式全程会计恒等式为 0；
8. 共享原料不足时无法超额排产；
9. 总排产无法超过共享产能。

### 3.3 建立核心玩法测试场景

应使用固定 seed 或直接构造状态，至少建立以下场景：

- 原料便宜、需求低；
- 原料昂贵、需求高；
- 订单充足、现货弱；
- 订单少、现货价格高；
- 某个共享原料短缺；
- 现金紧张但存在高利润机会；
- 多产品共同争夺合金、树脂等共享材料。

每个场景应检查是否存在至少两种合理策略，而不是只有一个显然最优解。

### 3.4 暂不优先处理的项目

在三环沙盘和核心数值尚未验证前，暂不建议继续扩展：

- 新事件；
- 新卡牌；
- 新知识产权；
- 新董事会目标；
- 新材料或新产品层级；
- 复杂财务指标；
- 完整模式的大规模数值重校。

### 3.5 核心成立后的增量恢复顺序

建议按以下顺序逐层恢复：

1. 设备；
2. 员工；
3. 融资；
4. 事件；
5. 研发；
6. 卡牌；
7. 董事会目标；
8. 成就与完整评分。

每恢复一层都应回答：

> 它是否给采购、生产或销售增加了新的决策，还是仅仅让数字变大？

如果只是线性数值增益，应考虑简化、合并或删除。

## 4. 已知风险与待确认问题

### 4.1 核心模式参数只是临时值

当前核心模式固定 4 个采购档、2 个订单、全产品解锁。这些设置的目的只是让三环能够立即运行，还没有经过平衡验证。

待确认：

- 基础采购档数应该是 3、4 还是按月变化；
- 每月订单数量和订单量；
- 哪些产品应在核心模式开局解锁；
- 初始产能、现金和库存；
- 是否保留高级产品所需的新材料开发。

### 4.2 核心模式目前跳过事件，市场月内变化不足

核心模式仍有季度气候变化，但不抽月度事件。因此同一季度内价格与需求可能较稳定。

这有利于先验证确定性核心，但之后需要确认核心市场输入应当如何变化：

- 固定场景；
- 月初公开市场卡；
- 只保留即时市场事件；
- 或保留气候但移除事件选择。

建议坚持“随机性在月初生成问题，玩家作出决策后不再随机否定结果”。

### 4.3 订单规则仍需重新验证

当前订单规则为当月产生、当月接取、当月交付，库存不足则部分交付并失效。该规则可运行，但尚未证明能产生足够的“确定订单 vs 风险现货”张力。

待确认：

- 订单是否应先于采购和生产展示；
- 订单是否需要违约惩罚；
- 订单价格是否一定高于现货；
- 订单是否占用自然需求；
- 是否需要跨月订单。现阶段不建议直接增加跨月复杂度，先验证当月模型。

### 4.4 销售目前仍偏自动结算

玩家能够分配销售资源和选择订单，但现货仍按需求自动成交。销售决策是否足够深尚未验证。

待确认：

- 销售资源用于扩量、提价还是获取订单；
- 同一种资源能否在这些用途间竞争；
- 是否需要玩家主动选择售价档位；
- 现货风险如何体现而不引入结算后随机惩罚。

### 4.5 多产品月末自动生产路径需要更多测试

玩家点击“确认生产”时，核心动作会为其他产品线预留共享原料。月末自动处理尚未确认的计划也支持多产品，但使用独立的内部 `maxProducible`，当前缺少共享原料冲突的专门测试。

建议：

- 优先要求玩家显式确认生产；
- 为月末自动生产增加共享原料冲突测试；
- 后续考虑提取统一的生产模拟/执行函数，避免 `actions.ts` 和 `settle.ts` 存在两份近似逻辑。

### 4.6 生产确认后不能撤销

当前确认生产会立即扣料并入库。这使生产成为不可逆动作，且玩家在调整销售计划后无法重新安排。

统一经营沙盘阶段需要确认：

- 是否继续采用“确认即执行”；
- 还是所有三环计划在月末统一执行；
- 或允许在结算前修改计划，仅在最终确认时统一过账。

从可读性和经营沙盘角度，倾向于“先规划、最后统一执行”，但这会影响当前即时生产记账路径，需单独设计。

### 4.7 实验分支不能长期与主干分叉

如果该分支持续数月，会导致完整模式和核心模式的状态、UI、结算逻辑发生漂移。完成经营沙盘和第一轮核心验证后，应尽快决定：

- 合并回主干；
- 继续迭代但定期变基；
- 或放弃实验并保留检查点。

## 6. 接手建议

接手者不应先调大量数值，也不应先恢复卡牌或事件。建议第一项任务直接实现 `previewOperations(state)` 或等价的统一经营预览，并以固定场景测试预览结果与真实结算是否一致。

判断下一阶段是否成功的标准不是 UI 是否更完整，而是玩家能否在结算前清楚回答：

1. 为什么采购这些原料；
2. 为什么选择这个产品组合；
3. 为什么接这些订单并把销售资源投到这些市场；
4. 如果更改其中一个决定，现金、库存、销量和毛利会怎样变化。

只有这四个问题在纯三环中成立，才值得继续恢复增量系统。
