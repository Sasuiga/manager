# 机制设计审查（德式重策视角）

> 审查范围：`docs/game_design.md`（规则）、`src/core/*`（引擎）、`src/data/game.ts`（数值）、`src/ui/*`（交互）、三个测试文件（audit/balance/route）。
> 结论先行：**骨架是一流的（会计恒等式全年零漂移、五档价格、采购档位、目标双轨都立得住），但决策层有三处结构性伤口，平衡层有"前松后紧错位"的硬伤，且约 15% 的卡牌文字是"死文本"。**

---

## 〇、总评

1. **引擎层**：`settle.ts` 的复式记账 + 移动加权平均 + 报表下钻是全项目皇冠，`audit.test.ts` 多种子全年恒等式 gap = 0，这在重策里是罕见的工程素质。
2. **决策层**：核心决策"生产布局"被简化成"单产品线 + 拉满"，UI 却在暗示多线分配；订单同月生成同月结算，一个月规划期都没有；事件阶段有静默叠加 bug。
3. **平衡层**：开局 100w 现金 + 20w 额度 + 0.8% 月息，让设计文档标榜的核心张力"现金流 vs 长期投入"在前 6 个月基本不生效（route 测试保守编制 0 破产）；主要败因是董事会目标（运气轴），不是资金链（规划轴）。
4. **文本层**：卡牌文案承诺了大量未实现的效果（死文本），对"卡组构筑"型游戏而言，每一张死文本都在撒谎。

---

## 一、结构性缺陷（引擎与规则咬合）

### 1.1 生产计划 = 单产品线（最重的伤）

- 状态：`plan: { tier, qty, overtime }`（`types.ts`），全月只持有一条线。
- `confirmProduction`（`actions.ts`）确认后 `plan.qty` 递减但**不追踪已用产能**：产能 20 时，先确认低端 14，再改计划中高端 14，两批共 28 件 —— 月产能约束形同虚设（只要玩家多点两次）。
- UI（`Turn.tsx` MakePage）文案"将产能分配到各产品线，可在已解锁产品线间自由腾挪"，但 `qty = on ? gs.plan.qty : 0` —— 切到新品线旧分配直接丢失；"剩余产能"数字在确认后也不修正。**UI 许诺了一个引擎并不存在的决策空间。**
- 数值上这个决策空间是真实的：气候中性月，"高端 3 + 低端 15"组合毛利 ≈ 88w/月 > 纯低端 58w/月。多线组合被引擎堵死，玩家只能"一条线拉满"。

**改法**：`plan` 改为 `plans: Record<Tier, number>` + 月度 `usedCapacity`；每线确认时扣产能与原料；UI 做成真正的 4 行分配矩阵（每行 stepper + 原料缺口提示 + 总产能条）。这是每月决策密度最高的一处，值得德式游戏级别的"布局面板"。

### 1.2 订单：同月生成、同月结算，`dueMonth` 是死字段

- `generateMonthlyOrders`（`engine.ts`）订单 `dueMonth = month + 1`，但 `settle()` 对 `state.orders` 全量消费且**从不读 dueMonth**（`remainingOrders` 声明后从未 push，结算后清空）。
- 文档 v1.2 的"自然订单：库存不足留到下月再判断"未实现（现为"部分交付 + 失效"），`SellPage` 的 hint 还写着"不足留到下月" —— 文档、UI、引擎三方互相矛盾。
- 后果：订单的"确定性"只剩"价格 +1 档"一点价值，没有跨月规划期，"为订单备货 vs 现货"的核心权衡被削平。

**改法**（推荐 A）：自然订单按 `dueMonth` 结算（本月生成、下月交付，库存不足可延期 1 次后失效）；强制订单（事件/卡）当月必交。这样恢复 1 个月规划期，订单系统才真正咬合生产计划。
（备选 B：规则简化为"订单当月事"，删掉 dueMonth 字段与全部相关文案。）

> **决议（2026-07 已确认）**：取备选 B——延期交付为历史设计、作废，至少现阶段不引入该复杂度（其他机制已提供足够决策密度）。见 `fix-plan.md` D4 / 阶段 1.2。

### 1.3 事件静默叠加（bug，影响约一半的月份）

- `App.tsx` 的 fallback：`if (phase !== 'operate' && phase !== 'report') beginMonthEvent(s)`。即时事件在 `beginMonthEvent` 内自动 resolved，于是 App 会**再抽一次事件**，循环直到抽到抉择/机会事件才停。
- 用 App 同一逻辑对 60 个种子 × 12 月做无头模拟：**552 个月中 270 个月叠加了 ≥2 张事件效果，129 个月叠加 ≥3 张**。玩家只看到最后那张（或一张都看不到），前面几张的供给/价格/需求修正在静默生效。
- 测试（audit/balance/route）都手动只调一次 `beginMonthEvent`，所以 bug 只活在 UI 流程里 —— 这正是"引擎对了、咬合错了"的典型。

**改法**：加 `state.flags['evStarted:' + month]` 守卫；或即时事件 resolved 后直接 `enterDraw`。

### 1.5 经济动能 = 死表，气候单调前进

- `MOMENTUM_ODDS`（各气候自己的扩张/停滞/收缩概率，`data/game.ts:112`）**从未被读取**；`advanceMonth` 用统一分布（P(+1)=49%, 0=36%, -1=7%, +2=7%, -2=1%）。
- 后果：气候环每季大概率前进 1 格 → 每局的宏观节奏几乎相同（只有起点偏移不同），"过热后大概率收缩、萧条后大概率复苏"的 intended feel 丢失，"每局不同"在经济轴上被削弱。
- 玩家可见的预测 `nextClimateOdds = 70/20/1` 既和真实分布不符，**又没有任何 UI 展示**（文档 §3.1.1 要求"预测下季度气候概率"）。

**改法**：先按当季气候用 `MOMENTUM_ODDS` 掷动能，再掷步长（1/0/2）；HUD 或董事会页展示真实分布（"下季：过热 49% / 滞涨 36%…"）。

### 1.6 订单与生产之外的两个小错位

- 采购"每类原料每月最多选一档" + 档数限制是好的身份感，但**贸易商每月基础就有 1~2 份报价**，C4 的"额外一次"反而成了死效果（见 1.4）—— 建议把基础贸易商改为"采购 2 人解锁"，C4 给 +1 份，层次干净。
- `grantOrder` 的订单层次选择是随机的（有库存的层），强制订单"到月必交"却可能落在玩家没产的层 → 建议强制订单只落在已解锁且上月有该层库存的层，或干脆按"上季结构"生成。

## 二、平衡缺陷

### 2.1 开局太容易，核心张力不生效

- 开局 100w（`START_CASH`）vs 第 1 月全部支出 ~35w（原料 31w + 招聘 ~4w）：不用卖货也能撑 3 个月。20w 基础额度 + 0.8% 月息 → 杠杆近乎免费。
- 证据：`route.test.ts` 保守编制 30 局 **0 破产**；`balance.test.ts` 30 局出局原因 **8/8 是"连续两季未达董事会目标"，资金为负 0 次**。设计文档的核心张力"短期现金流 vs 长期资产投入"在前 6 个月是休眠的。

**改法**（二选一，都可保持体验安全）：
- A：开局现金 100w → 60w（仍有 ~4 个月跑道）；
- B：现金保留 100w，但加"股东垫款"：第 3 月起每月强制还本 5w（计入财务费用/借款科目），把"借来的开局"变成一条真实还款线。
- 同时给借款加约束：最低还款（每月 10% 本金，可选，省利息）或季度"债务复审"（董事会动作）。

### 2.2 开局目标池失校 + 两个指标 bug

- B2"季度收入 ≥ 30w"：首月产能 10 × 6w = 60w，**开局目标池几乎全是白送分**。
- **B3"完成 1 次招聘"必败**：`hiresTotal` 只在季初董事会写入（`engine.ts:115`），`hire()` 从不递增它（`actions.ts:76` 写的是 `hireMonth:` 月度标记）→ 目标当前值恒等于季初累计，Q1 抽到 B3 = 必 miss（已用种子 1 验证：招完 1 人当前值仍为 0）。
- **C4"2 个月毛利 ≥ 4w"缺 `param`**（`OPENING_CHALLENGE C4`），按 `param ?? 0` 判定成"毛利 ≥ 0 的月份数" → 白送分。

**改法**：`hiresQ` 改为季度计数器（`hire()` 时递增，季初快照）；C4 补 `param: 40`；开局池按"零招聘基线"重校（B2 → 80~100w，C1 10w → 30w，C5 50w → 100w，C4 保持 4w）。

### 2.3 层级利润曲线不单调，真引擎挂在单张卡上

气候中性月、大批价、基准售价的月毛利上限：

| 层级 | 供给约束 | 月毛利 |
|---|---|---|
| 低端 | 产能（~20 件） | ~58w |
| 中端 | 合金 7 | ~28w（按代码 BOM 树脂 2） |
| 高端 | 芯片 3 | ~45w |
| 特殊 | 微机电 6（开发上限） | ~140w |

- 中端 < 高端 < 低端（总量），层级"升级感"断裂；真正引擎（特殊）需要：bom-special 研发（70 点、40% 基础成功率）**或** R6 逆向工程（需研发 3 人 + 卡还在牌堆里 —— R6 是 8 张普通卡随机取 6 中的一张，**1/4 的局里它根本不存在**）+ 两次供应商开发（各 3×(1AP+3w)）。终局体验被单张卡绑架，roguelike 味有了，但刷分游戏的"最优解"不该是掷骰子。
- **文档/代码不符**：§7.2.3 中端 BOM 是"1 树脂 + 1 合金（成本 6w）"，代码是树脂 2（成本 8w，`stdCost: 60` 的展示值还是错的）。
- route 测试也印证：保守编制中位分 **174** > 激进编制 **164** —— 多花的钱（研发 2 人、精密产线、销售 4 人）12 个月内没赚回来，**刷分体系在惩罚投资**，与"引擎构筑：从弱到强，后期爆发"的定位矛盾（盈利分系数 1.5 > 资产分 1.0，12 个月视野下前期利润 > 期末资产）。

**改法**：
- 中端 BOM 对齐文档（树脂 1 + 合金 1，单位毛利 6w，层级单件毛利恢复单调：2.9 < 6 < 15 < 23.3w）；
- 芯片基础供给 3 → 4（高端 4 件/月 ≈ 60w，追平低端，成为真实的中后期选项）；
- bom-special 基础成功率 40% → 50%，或 R6 保证每局入堆（8 选 6 → 8 选 5，R6 必入）；
- 刷分权重：盈利分系数 1.5 → 1.2、资产分 1.0 → 1.5（奖励把利润沉成资产），或把盈利分改成"末季年化"而不是 12 个月累计（前 3 个月的 tutorial 利润不该占 1/4 权重）。

### 2.4 部门轨道价值不对称：生产线永远是最佳性价比

- 生产人员：**招聘费 0**（`hireFees: [0]`）+ 月薪 0.5w + 产能 +4~+7/人；其他部门 5w→1w 阶梯招聘费 + 1~2w 月薪。同一 AP，生产线的"轨道推进"成本只有别人 1/3~1/5 → "专精 vs 均衡"张力在数值上被结构性地偏向专精生产。
- 销售是最贵轨道（1.5w 月薪 + 5w 起步招聘费）但销售资源池又是全局约束（满配需求上限 69 点 > 资源池 38~41 点）—— 最贵的轨道卡着最紧的约束，进一步劝退均衡流。

**改法**：生产人员加一次性招聘费 2w（或阶梯 3/2/1），保留"便宜但不白送"；销售 4 人门槛的资源贡献 +6 → +8，把"贵"兑现。

### 2.5 设备 2.5 个月提足折旧，固定资产是幻影

- 标准产线 5w 成本 / 2w 月折旧 = **2.5 个月提足**（`EQUIPMENT_SHOP`）。资产侧的"固定资产"科目对玩家几乎是装饰。
- 与"每台设备带来 5w 借款额度（3 个月）"的信贷语义也不匹配。

**改法**：月折旧 20 → 5（24 个月提足），事件 D9"折旧减半"随之调整为 2.5w/月；设备净值曲线变平，资产分更真实。

## 三、体验与可读性（德式游戏靠"玩家能预测系统"活着）

1. **没有存档**：12 月 × 8 阶段，一次刷新回标题。状态全量可序列化（`rngState` + 纯数据）→ 每月结算后 JSON 存 localStorage；标题页支持输入 seed（刷分/排行榜都需要 seed 可比性）。
2. **HUD 缺"预估总分"**：设计系统 `design-system.md §4.5` 已经预留了"预估分（金）"stat 盒，但 `Hud.tsx` 只有现金/AP/提案。刷分游戏最核心的仪表是"我这一局大概多少分"，加实时预估（累计净利×系数 + 当前净资产×系数 + 目标 + 成就）成本极低。
3. **事件面板信息残缺**：`Event.tsx` 的即时事件面板只显示需求/产能/采购档数，原料档位与利率变化全靠读文案记。加一行"本月价格档位：包材 基准→低 …"。
4. **早月销售加点无价值**：产能 10 时低端需求 15 永远供不满，10 点基础资源里 ~5 点是死的。接受为"前 2 个月教程"即可，或基础销售资源 10 → 6，让第一个加点决策有意义。
5. **目标 UI 的小坑**：`goalProgress` 对 lte 型目标（负债 ≤ X）的进度条是 `t/current`，current=0 时返回 1（达标）—— 语义对，但"负债 0 / 上限 15w"的展示要写清楚分母，避免玩家误读。

## 四、建议保留（别动骨架）

- 复式记账 + 移动加权平均 + 报表下钻（audit 零漂移是工程皇冠）；
- 五档价格体系（气候/事件/卡只改档位不改百分比，可读性极佳）；
- 采购档位（小批/中批/大批 × 档数上限）—— 采购部的身份感来源；
- 销售 push 点的成本梯度（v1.2 改对了："推哪层"是真规划题）；
- 董事会双轨目标 + 绝对数/比率分列（§4.5 的展示规则设计得很好）；
- 成就 = 部门满员（轨道锚点，和盖亚计划式的轨道语言一致）。
